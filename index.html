3. Introduction to State Design Pattern

A beginner-friendly guide to understanding dynamic object behaviors.

💡

What is the State Pattern?

Think of a Smartphone. When it is Locked, tapping the screen shows the clock. When it is Unlocked, tapping the screen opens an app.

The phone is the exact same object, but its behavior changes completely depending on its current state. The State Design Pattern brings this exact real-world concept into software programming.

🎯

Core Idea in Simple Terms

"Instead of putting all state logic into one giant file with lots of if-else checks, put each state's rules into its own separate class."
  • Every state (like Idle or Dispensing) gets its own dedicated class.
  • The main machine delegates work to whichever state class is currently active.
  • State transitions happen smoothly by swapping active state objects.

4. What Problem Does it Solve?

Say goodbye to "Spaghetti Conditionals" and unmaintainable code.

❌ WITHOUT STATE PATTERN

Messy If-Else Spaghetti

User Action
➔
if (state == IDLE) { ... }
else if (state == HAS_MONEY) { ... }
else if (state == DISPENSING) { ... }

Adding a single new state forces you to edit every method in your code, leading to bugs and hard-to-read programs.

✅ WITH STATE PATTERN

Clean Object Delegation

User Action
➔
Context (Machine)
➔
Active State Object

The main machine doesn't care about state rules. It simply forwards the request to the active state class.

❌ Bad Approach: Multi-branch Conditionals 
// Hard to read & risky to modify!
public void selectProduct() {
  if (state == IDLE) {
    print("Insert money first!");
  } else if (state == HAS_MONEY) {
    state = PRODUCT_SELECTED;
    print("Product chosen.");
  } else if (state == DISPENSING) {
    print("Please wait, dispensing!");
  }
}
✅ Good Approach: State Pattern Polymorphism 
// Simple, clean, & 100% modular!
public void selectProduct() {
  // Delegate directly to the current state object
  currentState.selectProduct(this);
}

5. How Behavior Changes Based on State

A step-by-step walk-through of state delegation.

1

User Triggers Action

The user presses a button (like "Insert Money" or "Select Product") on the main Context machine.

2

Context Forwards Call

The Context machine doesn't execute logic directly. It passes the request to its currentState instance.

3

Active State Responds

Whichever state is active (Idle, HasMoney, etc.) executes its custom response logic for that action.

4

State Switch Occurs

If the action is valid, the state object tells the Context to swap to the next State object (e.g., Idle ➔ HasMoney).

6. Basic Structure of the State Pattern

The 3 essential building blocks that make up the pattern.

Building Block 1
🏛️

Context

(e.g., Vending Machine)

The primary class the user interacts with. It holds a variable pointing to the current state and delegates actions to it.

Building Block 2
📋

State Interface

(e.g., VendingMachineState)

The blueprint interface listing all actions that can be performed (like insertMoney(), selectProduct(), dispense()).

Building Block 3
⚙️

Concrete States

(IdleState, HasMoneyState, etc.)

Separate classes implementing the State Interface. Each class defines how the machine behaves in that specific state.

7. UML Class Diagram

Canonical architectural structure and realization of the State Design Pattern.

🧩 Role of Each Component in the Pattern

1. Context

Context (e.g., VendingMachine)

The primary class that clients interact with. It maintains an internal reference to a State object representing its current state.

  • Delegates incoming requests directly to currentState.handle().
  • Exposes a setState(newState) method so concrete states can trigger transitions.
2. State Interface

State Interface (VendingMachineState)

An interface or abstract class defining the common API contract for all state behaviors.

  • Declares state-dependent methods (e.g., insertMoney(), dispense()).
  • Ensures all concrete state classes implement the exact same set of methods.
3. Concrete States

Concrete States (ConcreteStateA, B, C)

Individual classes implementing the State interface. Each class contains custom logic for one specific state.

  • Executes custom response logic when an action is invoked in that state.
  • Swaps the Context's active state object when valid conditions are met.

8. Real-World Example: Vending Machine

Relating state transitions to physical everyday interactions.

1. IDLE

Waiting for Customer

The machine is waiting for coins/cash. You cannot press dispensing buttons yet because no money has been accepted.

2. HAS_MONEY

Money Accepted

The machine displays balance. Now you can select a snack or press "Cancel / Refund" to return cash.

3. PRODUCT_SELECTED

Product Reserved

The machine verifies price & stock. You can now press "Dispense" to complete purchase.

4. DISPENSING

Releasing Item

The mechanical motor spins, drops the snack, returns change, and automatically resets machine state back to IDLE.

10. Java Implementation

Clean, production-ready Java code implementing the State Pattern.

public class VendingMachine {
    private VendingMachineState idleState;
    private VendingMachineState hasMoneyState;
    private VendingMachineState productSelectedState;
    private VendingMachineState dispensingState;

    private VendingMachineState currentState;
    private double balance = 0.0;
    private String selectedProduct = "";

    public VendingMachine() {
        idleState = new IdleState();
        hasMoneyState = new HasMoneyState();
        productSelectedState = new ProductSelectedState();
        dispensingState = new DispensingState();

        currentState = idleState; // Default initial state
    }

    // Delegates to current state object
    public void insertMoney(double amount) {
        currentState.insertMoney(this, amount);
    }

    public void selectProduct(String product, double price) {
        currentState.selectProduct(this, product, price);
    }

    public void dispense() {
        currentState.dispense(this);
    }

    public void refund() {
        currentState.refund(this);
    }

    // State mutation helpers
    public void setState(VendingMachineState newState) {
        this.currentState = newState;
    }

    public double getBalance() { return balance; }
    public void addBalance(double amt) { this.balance += amt; }
    public void setBalance(double amt) { this.balance = amt; }

    public VendingMachineState getIdleState() { return idleState; }
    public VendingMachineState getHasMoneyState() { return hasMoneyState; }
    public VendingMachineState getProductSelectedState() { return productSelectedState; }
    public VendingMachineState getDispensingState() { return dispensingState; }
}
public interface VendingMachineState {
    void insertMoney(VendingMachine machine, double amount);
    void selectProduct(VendingMachine machine, String product, double price);
    void dispense(VendingMachine machine);
    void refund(VendingMachine machine);
}
public class IdleState implements VendingMachineState {
    @Override
    public void insertMoney(VendingMachine machine, double amount) {
        machine.addBalance(amount);
        System.out.println("Accepted $" + amount);
        machine.setState(machine.getHasMoneyState());
    }

    @Override
    public void selectProduct(VendingMachine machine, String product, double price) {
        System.out.println("Error: Insert money first!");
    }

    @Override
    public void dispense(VendingMachine machine) {
        System.out.println("Error: Insert money and select product first.");
    }

    @Override
    public void refund(VendingMachine machine) {
        System.out.println("Error: No money to refund.");
    }
}
public class HasMoneyState implements VendingMachineState {
    @Override
    public void insertMoney(VendingMachine machine, double amount) {
        machine.addBalance(amount);
        System.out.println("Added $" + amount + ". Total: $" + machine.getBalance());
    }

    @Override
    public void selectProduct(VendingMachine machine, String product, double price) {
        if (machine.getBalance() < price) {
            System.out.println("Insufficient balance! Product costs $" + price);
            return;
        }
        System.out.println("Product " + product + " selected.");
        machine.setState(machine.getProductSelectedState());
    }

    @Override
    public void dispense(VendingMachine machine) {
        System.out.println("Error: Select a product first.");
    }

    @Override
    public void refund(VendingMachine machine) {
        System.out.println("Refunding $" + machine.getBalance());
        machine.setBalance(0);
        machine.setState(machine.getIdleState());
    }
}
public class ProductSelectedState implements VendingMachineState {
    @Override
    public void insertMoney(VendingMachine machine, double amount) {
        machine.addBalance(amount);
    }

    @Override
    public void selectProduct(VendingMachine machine, String product, double price) {
        System.out.println("Updated selection to: " + product);
    }

    @Override
    public void dispense(VendingMachine machine) {
        System.out.println("Dispensing item...");
        machine.setState(machine.getDispensingState());
        machine.dispense(); // Trigger dispensing logic
    }

    @Override
    public void refund(VendingMachine machine) {
        System.out.println("Refunding $" + machine.getBalance());
        machine.setBalance(0);
        machine.setState(machine.getIdleState());
    }
}
public class DispensingState implements VendingMachineState {
    @Override
    public void dispense(VendingMachine machine) {
        System.out.println("Item successfully dropped into tray!");
        machine.setBalance(0);
        // Transition back to IDLE after dispensing
        machine.setState(machine.getIdleState());
    }

    @Override
    public void insertMoney(VendingMachine machine, double amount) {
        System.out.println("Please wait, currently dispensing!");
    }

    @Override
    public void selectProduct(VendingMachine machine, String product, double price) {
        System.out.println("Please wait, currently dispensing!");
    }

    @Override
    public void refund(VendingMachine machine) {
        System.out.println("Cannot refund during dispensing.");
    }
}

💡 Beginner-Friendly Class Breakdown

Interface

1. VendingMachineState

The blueprint interface declaring insertMoney, selectProduct, dispense, and refund methods that every state must implement.

State 1

2. IdleState

Initial state. Accepts money and switches state to HasMoneyState. Blocks product selection and dispensing since no money is inserted.

State 2

3. HasMoneyState

Money has been inserted. Accepts product selection if balance and stock are valid, switching to ProductSelectedState. Allows refunding cash.

State 3

4. ProductSelectedState

Product is reserved. Clicking dispense() switches state to DispensingState. Allows changing product selection or refunding cash.

State 4

5. DispensingState

Item is being delivered into the chute. Rejects all actions while motor spins, returns change, and resets machine back to IdleState.

Context

6. VendingMachine

The main machine class. Holds `currentState` reference and delegates all actions (`insertMoney`, `dispense`, etc.) directly to the active state class.

11 & 12. Tradeoffs: Advantages vs Disadvantages

Weighing the benefits against architectural overhead.

⚡

11. Key Advantages

  • Single Responsibility Principle (SRP): Keeps code organized by isolating state-specific logic into distinct classes.
  • Open/Closed Principle (OCP): Introduce new states without modifying existing state classes or context logic.
  • Eliminates Conditionals: Replaces ugly, repetitive if/else or switch blocks with clean polymorphism.
  • Explicit State Transitions: Makes state transition rules explicit rather than buried inside flag variables.
⚠️

12. Potential Disadvantages

  • Class Explosion: Can be overkill if a machine only has 2 simple states that rarely change.
  • Increased Complexity: Requires creating multiple small files and interfaces.
  • Context Coupling: State classes need references back to the Context object to trigger state switches.

13. When to Use the State Pattern

A practical checklist for software architects.

✅ Use State Pattern When:

  • You have an object whose behavior changes dynamically based on its internal state.
  • Your methods contain large multi-branch conditional statements (if-else / switch) dependent on state flags.
  • State transition rules are complex and need to be isolated and unit-tested independently.
  • Examples: Order Processing (Pending -> Paid -> Shipped -> Delivered), Audio Player (Playing -> Paused -> Stopped), Game AI (Idle -> Patrol -> Attack).

⛔ Avoid State Pattern When:

  • The state machine has only 1 or 2 states with minimal state-dependent logic.
  • The states rarely change and simple boolean flags suffice.
  • Performance is ultra-critical and object instantiation overhead is a concern.
